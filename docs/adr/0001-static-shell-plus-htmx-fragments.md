# 페이지는 정적 HTML, 상호작용은 htmx 조각으로 한다

2026-09-02 · 확정

## 결정

- 페이지 껍데기(제목·탭·입력칸·안내·노선 목록 표)는 빌드 때 한 번 만들어 Cloudflare Pages에 올린다.
- 사용자가 무언가를 고를 때마다 htmx가 HTML **조각**을 받아 `hx-target` 자리에 끼운다. JSON을 받아
  브라우저가 그리는 방식은 쓰지 않는다.
- 조각의 출처는 탭에 따라 다르다. 장소 탭은 Cloudflare **Worker**가 **D1**을 읽어 요청마다 만든다.
  노선번호 탭은 빌드 때 만든 정적 파일이다(ADR-0002).
- 지도는 예외다. htmx는 지도를 못 그리므로 지도 타일·경로선·점은 Kakao JS SDK가 브라우저에서 그린다.
  Worker는 좌표만 조각에 실어 보낸다.

## 왜

목업(Hacker_AI)은 Next.js 정적 내보내기였다. 브라우저가 노선망 JSON 1.3MB를 통째로 받아 스스로
경로를 계산했고, 서버 코드는 0이었다. 목업으로 화면 배치와 용어는 굳었으나, 본 구현은 "정적 페이지와
동적 페이지를 함께 쓰는 웹"으로 새로 시작하기로 했다(사용자 결정).

htmx를 고른 이유는 **서버가 HTML을 돌려주면 브라우저 쪽 코드가 거의 없어진다**는 점이다. 목업의
`'use client'` 컴포넌트 9개가 하던 상태 관리가 사라지고, 화면 = 정적 HTML + 조각 HTML이 된다.

Worker + D1을 고른 이유는 장소 탭의 입력(좌표 쌍)이 무한이라 빌드 때 답을 미리 만들 수 없기
때문이다. 이미 Pages를 쓰고 있으니 같은 계정의 Worker와 D1이 배포·과금·키 관리에서 가장 짧은 길이다.

## 뒤집히는 목업 결정

- 목업 ADR-0001(경로 계산은 브라우저에서) → 장소 탭 계산은 Worker에서
- 목업 ADR-0008(Kakao 키는 브라우저에 나가고 도메인 화이트리스트로 막는다) → 장소 검색은 Worker가
  대신 호출하므로 REST 키는 서버에만 있다. 지도용 JS 키는 여전히 브라우저에 나간다

## 대가

- Worker가 멈추면 장소 탭이 멈춘다. 노선번호 탭은 영향 없다(ADR-0002).
- Worker 무료 요금제의 요청당 CPU 시간 제한 안에 경로 계산이 들어가는지 **실측이 필요**하다.
  목업 실측(중앙값 3ms, 최악 130ms 안팎)은 브라우저에서 잰 값이라 그대로 믿지 않는다.
