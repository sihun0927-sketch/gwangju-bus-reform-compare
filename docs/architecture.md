# 구조 (2026-09-02 설계 확정본 · 2026-09-03 장소 탭 Worker 확정)

이 문서는 세션 맥락 없이 읽혀야 한다. 용어는 `CONTEXT.md`, 결정의 근거는 `docs/adr/`.
모듈 지도와 화면 목업은 `docs/images/`에 PNG로 있고(README에 실려 있다), 아트보드 원본은
`docs/canvas/*.dc.html`이다 — `python tools/render_canvas.py`로 다시 뽑는다.

## 1. 한 문장

**정적 HTML 껍데기 + htmx 조각.** 페이지는 빌드 때 한 번 만들어 Cloudflare Pages에 올리고,
사용자가 무언가를 고를 때마다 htmx가 HTML 조각을 받아 그 자리에 끼운다. 조각은 두 종류다 —
노선번호 탭은 **빌드 때 만든 정적 파일**, 장소 탭은 **Worker가 번들 JSON을 읽어 만드는 동적 응답**(ADR-0008, D1 없음).

계산은 빌드 스크립트(노선번호 탭)와 Worker(장소 탭)가 하고, 브라우저는 HTML만 받는다.

## 2. 부품과 역할

| 부품 | 무엇 | 이 프로젝트에서 하는 일 | 어디에 |
|---|---|---|---|
| **Cloudflare Pages** | 정적 파일 창고 | `out/` 전체를 냄. 껍데기, 노선 개편 목록 표, 노선번호 탭 조각 308개(카드 103 + 표 205), CSS 한 장, 브라우저 스크립트 둘(`place.js` · `map.js`) | 배포 |
| **Cloudflare Worker** | 요청마다 실행되는 JS 서버 | 장소 탭 셋: `GET /places?q=`(Kakao REST 대리 호출) · `GET /compare?from=&to=`(경로 계산 → 카드 한 쌍 + 경로 지도 좌표 + 다른 경로 키) · `GET /journey/{id}`(경로 키를 풀어 다른 경로 카드 하나 + 그 경로의 좌표). 그리고 자료 경로 하나: `GET /headway?route=`(배차간격 추정 + 답변 뼈대, **조각이 아니라 JSON** — ADR-0010) · `GET /headway/{노선}`(추론을 거친 배차간격 조각, 카드의 「계산중…」을 대신한다 — ADR-0011). 정적 자산과 같은 Worker, `run_worker_first` 다섯 경로 | 배포 |
| **번들 JSON** | Worker와 함께 배포되는 데이터 파일 `worker/data.json` | 정류장(줄 단위)·노선망·환승 쌍·노선 쌍별 환승 지점. 약 1MB. Worker만 읽는다. ~~D1~~은 쓰지 않는다(ADR-0008) | Worker 번들 |
| **추론 층** | Worker 안에서 모형을 부르는 부품 `worker/infer.js` | 카드의 배차간격 칸을 채운다. 배차간격 표를 근거로 주고 **표본 셋의 중앙값**을 밴드 안에 가둬 낸다. 제공자는 OpenAI(`chat.completions.parse` + 구조화 출력 + 낮은 온도). 키가 없으면 안 부르고 계산값을 보인다(ADR-0011) | Worker |
| **배차간격 표** | 번들과 따로 두는 작은 데이터 파일 `worker/headway.json` | 개편 후 노선 118개의 배차간격 추정 · 밴드 · 등급과 망 전체 차량 수지. 32KB. **같은 글이 `out/headway.json`으로도 나가** 주소 하나로 통째로 받아 갈 수 있다(ADR-0010) | Worker 번들 · `out/` |
| **빌드 스크립트** | 배포 전 한 번 도는 프로그램 | `data/source/`의 CSV 8개(시 공표 6 + `stops.csv` + 배차간격) → 정적 조각 파일 + 번들 JSON. 노선 변화 표 규칙과 환승 쌍·노선 쌍 계산이 여기 | `tools/` |
| **htmx** | `hx-*` 속성 라이브러리 | 버튼·목록 줄에 붙어 조각 URL을 받아 `hx-target`에 끼움. 페이지 새로고침 없음. 껍데기가 CDN 스크립트 태그 하나로 부르고 SRI로 고정한다 | 브라우저 |
| **Kakao JS SDK** | 지도 | 지도 타일과 경로선·점을 **브라우저에서** 그림. htmx는 지도를 못 그린다. JS 키는 브라우저에 노출, 도메인 화이트리스트로 방어(ADR-0005) | 브라우저 |
| **Kakao REST API** | 장소 검색 | Worker가 대신 호출. REST 키는 Worker 환경 변수에만 둔다(ADR-0005) | Worker |

## 3. 두 탭의 정적 / 동적 분할

번호는 캔버스 아트보드의 번호와 같다. 회색 실선 = 정적, 초록 점선 = 동적.

### 3-1. 장소로 찾기 (캔버스 페이지 1)

| 번호 | 영역 | 정적/동적 | URL | 만드는 곳 |
|---|---|---|---|---|
| ① | 껍데기: 제목·탭·출발/도착 입력칸·안내 | 정적 | `index.html` | 빌드 |
| ④ | 자동완성 후보 (장소, 입력 중) | 동적 | `GET /places?q=전남대` → `<ul>` | Worker → Kakao REST |
| ⑤ | 경로 지도 자리 + 개편 전 카드 / 개편 후 카드 (머리에 상태, 판정 문장 없음) + 기본 경로의 좌표 · 다른 경로 키 | 동적 | `GET /compare?from=lat,lng&to=lat,lng` | Worker → 번들 JSON → 경로 계산 |
| ⑥ | 다른 경로 카드 하나 + 그 경로의 좌표 | 동적 | `GET /journey/{id}` | Worker. 선 긋기는 Kakao JS |

흐름: 껍데기 → 입력 → ④ → 선택 → ⑤ → 펼침 → ⑥. `map`이 ⑤·⑥의 좌표로 경로 지도를 그리고, 「지도에 표시」로 카드마다 올릴 경로 하나를 고른다(2026-09-04). 예시 쌍 버튼은 두지 않는다(캔버스에서 삭제).

### 3-2. 노선번호로 찾기 (캔버스 페이지 2)

| 번호 | 영역 | 정적/동적 | URL | 만드는 곳 |
|---|---|---|---|---|
| ① | 껍데기: 노선번호 입력칸·안내 | 정적 | `index.html` | 빌드 |
| ② | 노선 개편 목록 표 103행 (개편 전 · 개편 후) | 정적 | `index.html` 안에 통째로 | 빌드 |
| ④ | 자동완성 후보 (번호 103개, 값 = 번호 · 설명 = 대체 노선) | 정적 | `index.html` 안 `<datalist>`. 고르면 htmx `path-params` 확장이 `route/{number}.html`을 부름 | 빌드 |
| ⑤ | ~~표 필터~~ | — | 없음(2026-09-04). 표는 늘 103행, 좁히기는 ④가 맡는다 | — |
| ⑥ | 노선 변화 카드: 제목·대체 노선·방면 선택·대체 노선 선택·요약 칸·노선 지도 자리 | **정적 조각** | `route/{번호}.html` | 빌드 (ADR-0002) |
| ⑦ | 노선 변화 표 + 노선 지도 좌표 JSON(상행, 줄마다 상태) | **정적 조각** | `route/{번호}/{개편 전 방면}/{대체 노선}/{개편 후 방면}.html` | 빌드 (ADR-0002, 0003, 0006) |

흐름: 입력 → ④ → 번호 확정 → ⑥ → 방면·대체 노선 고름 → ⑦ → `map`이 ⑦의 좌표로 노선 지도를 그림.
조망 지도(버스가 오지 않는 정류장)는 두지 않는다(캔버스에서 삭제). **이 탭은 Worker 없이 돈다** — 브라우저
스크립트는 `map` 하나(두 탭 공용)뿐이다.

## 4. 데이터 흐름

```
data/back_up/api_stops.json (API 응답 원본, ADR-0007)
        │  tools/build_stops.py
        ▼
data/source/*.csv (시 공표 6 + stops.csv 좌표 4,746개)   data/name_canon.json (이름 잇기 8)
        │                                                       │
        └──────────────────────┬────────────────────────────────┘
                               ▼
              tools/build.*  (빌드 스크립트)
        ┌──────────────┴───────────────────────────┐
        ▼                                          ▼
 out/                                       worker/data.json (번들 JSON)
   index.html        ← 껍데기 + 노선 개편 목록 표      정류장 · 노선망 · 환승 쌍 · 노선 쌍
   route/문흥18.html ← ⑥ 결과 카드                       │
   route/문흥18/기본/간선18/기본.html ← ⑦ 표              ▼
   route/문흥18/기본/지선10/기본.html               Worker(import) ◄── htmx (장소 탭)
   … (카드 103 · 표 205, ADR-0006)
        │
        ▼
 Cloudflare Pages ◄── htmx (노선번호 탭)
```

빌드 스크립트의 단계(노선 변화 표 부분, ADR-0003):

0. **번호 잇기** — 노선 표기를 (종류, 번호, 방면)으로 갈라 비교표와 노선안을 잇는다(ADR-0006). 못 찾는 쌍 0
1. **명칭 사전** — `명칭 변경 정류소.csv`에서 옛 이름 → 새 이름 집합. 옛 이름 하나에 새 이름 여럿 허용
2. **방면 분리** — 같은 종류+번호의 행을 방면으로 나눔. 개편 전 6개 번호 14행, 개편 후 지선97
3. **기·종점 정렬** — 개편 전 방면 × 대체 노선 × 개편 후 방면 쌍(205)마다 ① 기·종점 이름 → ② 정류장 겹침 → ③ `data/기종점정렬표.csv`
4. **기·종점 정류장 대조** — 상행끼리·하행끼리 최장 공통 부분열(LCS)로 정렬. 명칭 사전을 적용해 이름이 다른 같은 정류장을 「유지」로
5. **비고** — 명칭 변경 · 통폐합 · 이전 · 신설 (CSV 사실만. 상태는 적지 않는다)
6. **파일 쓰기** — `route/{번호}.html`, `route/{번호}/{개편 전 방면}/{대체 노선}/{개편 후 방면}.html`

## 5. 노선 변화 표 규격

캔버스 페이지 3에 문흥18 ↔ 간선18 실제 값으로 그려져 있다.

| 항목 | 규격 |
|---|---|
| 열 | `# · 개편 전 상행 정류장 · 개편 후 상행 정류장 · 개편 전 하행 정류장 · 개편 후 하행 정류장 · 비고` |
| 줄 | 정류장 이름을 순서대로 맞댄 것. 위에서 아래로 읽으면 버스가 가는 순서 |
| 색 | 개편 전에만 있는 줄 = `--worse-bg`(붉은 바탕), 개편 후에만 = `--better-bg`(초록 바탕). 글자 굵기는 같다 |
| 상태 | 유지 / 경유 제외 / 경유 추가. 주어는 노선 — 정류장이 없어진 것이 아니다. 화면에는 줄 색·범례·요약 칸에만 나온다 |
| 상행·하행 요약 칸 | 상행·하행 각각 유지/경유 제외/경유 추가 셋 = 여섯 칸, 같은 크기로 나란히. "상행 · 경유 제외 11곳" |
| 버튼 줄 | 개편 전 방면 선택(6개 노선만) / 대체 노선 선택 `[간선18] [지선10]` / 개편 후 방면 선택(대체 노선에 방면이 있을 때만) |
| 하행 없는 노선 | 하행 두 칸을 비우고 비고에 "순환 노선 · 하행 없음" 또는 "편도 운행 · 하행 없음". 열은 늘 여섯 |
| 방향 표시 | 기·종점 정렬에서 뒤집어 맞댄 경우, 표 아래에 "기점·종점이 반대라 뒤집어 맞댔습니다" 한 줄 |
| 제목 | 「<번호(방면)> 노선 변화」. 예: 「두암81(각화초교.장등동) 노선 변화」 |
| 출처 줄 | "출처: 광주광역시 시내버스 노선개편안 「노선개편 전·후 비교표」 · 「광주권역 개편전/개편후 노선안」" |

### 6-4. `/compare` 요청당 CPU (2026-09-04, `tools/measure_cpu.mjs`)

**요금제 판정은 이 표로 한다.** §6-3은 이 PC의 Node에서 잰 벽시계라 위에 적은 대로 재현되지 않고,
Workers가 세는 것은 벽시계가 아니라 아이솔레이트 안에서 실제로 돈 CPU다.

## 8. 미결

- **`절골입구`는 `(북)`으로 둔다.** `(서)`와 약 40m라 도보권 500m·환승 도보 350m 판정을 바꾸지 않는다(2026-09-03 확인).
- **`stops.csv`의 이름·ARS_ID가 노선안·명칭 변경 CSV와 어긋나는 자리.** 셋을 확인했다(2026-09-04).
  ① 같은 이름이 여러 고을에 있다(§6) — 노선 지도는 노선을 따라 고르지만 `bundle`의 `route_stops`는
  아직 그 이름의 줄을 **전부** 달아 두므로, 장소 탭 경로 계산이 이 이름을 만나면 다시 봐야 한다.
  ② 명칭 변경 CSV의 ID가 `stops.csv`의 다른 정류장을 가리키는 행이 있다 — 돈보스코학교 → 하남고등학교의
  ID 5936은 `stops.csv`에서 「비아동주민센터(앞)」이고, 옳은 줄은 ID 5964뿐이다(5km 차이).
  ③ 이름이 `stops.csv`에 한 줄뿐인데 그 줄이 노선에서 멀리 떨어진 것이 있다(지선92의 「석계」, 왕복 20km).
  고를 것이 하나뿐이라 지도가 바로잡을 수 없다. 시 자료나 BIS가 고쳐지면 다시 본다
- **신설 정류소 57개의 좌표.** `source/stops.csv`에 없다(신설 56 + `광주교대역2번출구`). 개편 후 BIS가 열리면
  다시 받고, 그때까지는 비워 둔다 — 지어낸 좌표를 넣지 않는다(ADR-0007)
- 🔴 **`/compare`의 요청당 CPU가 무료 요금제 상한을 넘는다. 재는 일은 끝났고 줄이는 일이 남았다**(티켓 6).
  workerd에서 잰 값이 **중앙값 20.2~21.2ms · p90 31.8ms**, 상한 10ms를 넘는 요청이 **120개 중 108~116개**다(§6-4).
  프로파일러 몫을 깎아도 두 배라, 「거의 든다」가 아니라 **구조를 바꿔야 드는 자리**다.
  이전 판(281ms)에서 둘을 줄였고 — ① 노선 쌍의 환승 지점과 그 자리의 방향·순번을 모듈 초기화 때 붙여 두기
  ② 표를 찾는 열쇠를 그때 함께 만들어 두기(요청 때 글자를 안 잇는다) — 셋째로 **손에 든 칸 추리기**(같은
  노선·방향에서 점수와 순번이 둘 다 뒤지면 버린다)는 **되돌렸다**. 링크 훑기는 35% 주는데 이 PC에서 시간
  차이가 잡음에 묻혔고(중앙값 35.7 vs 37.3ms), 「다른 경로」(티켓 5)에 쓸 2·3등이 나빠진다(노선 조합
  277 → 187, 한 쌍에서 2등이 17분 → 18분).

  **원인은 두 곳뿐이다 — `walkableStops`와 `갈아탄다`가 CPU의 80%다**(§6-4). 나머지를 다 없애도 4ms가
  줄 뿐이라, 손댈 곳은 이 둘이고 그 밖은 손대지 않는다. 줄일 곳을 싼 것부터 적는다.

  1. **도보권 후보를 격자로 좁힌다**(`walkableStops`, ~40%). 지금은 지점 하나마다 그 노선망이 서는 정류장
     (개편 전 2,977줄 · 개편 후 2,873줄)을 **전부** 훑으며 하버사인을 잰다. 요청 하나에 지점 둘 × 노선망
     둘 = 네 번, 거리를 만 번 넘게 재는 셈이다. 그런데
     쓸 것은 1,000m 안뿐이다. `network`가 모듈 초기화 때 정류장을 위도·경도 격자에 담아 두면 요청 때는
     둘레 칸만 보면 된다. **셈을 안 바꾸고 훑는 수만 줄이는 것**이라 답이 그대로인 것을 검사로 묶기 쉽다
     — 지금 검사가 기대하는 후보 목록이 바뀌면 안 된다.
  2. **환승 상대를 미리 걸러 둔다**(`갈아탄다`, ~40%). 손에 든 칸마다 그 노선의 `route_links`를 전부 돌며
     `이른_순번`을 부른다. 두 바퀴째에는 손에 든 칸이 수천이라 이 곱이 통째로 늘어난다. 초기화 때 노선 쌍의
     `hereRides`를 **방향별로 순번순으로** 정렬해 두면 `이른_순번`이 훑기에서 이분 탐색이 되고, 방향이 없는
     쌍은 아예 목록에서 빠진다.
  3. **그래도 안 들면 환승 2회를 손본다.** 위 둘은 같은 답을 더 빨리 내는 것이고, 이것은 **답이 바뀐다** —
     그래서 마지막이다. 상한을 1회로 낮추면 §6-3의 「환승 2회」 346·301쌍이 통째로 답을 잃는다. 대신
     노선망마다 답이 나온 뒤 두 바퀴째를 멈추는 식이라면 잃는 것이 적을 수 있는데, 얼마를 잃는지는
     `tools/measure_search.mjs`가 재 준다. **재기 전에는 고르지 않는다.**

  판정은 `tools/measure_cpu.mjs`로 다시 한다. 하나 고칠 때마다 돌려 §6-4를 갈아 끼운다
- **거리를 재는 셈이 두 곳에 있다.** ADR-0008은 규칙 상수를 `worker/rules.js` 한 곳이라 정했는데, 빌드는
  파이썬이라 그 파일을 import할 수 없어 `tools/build/bundle.py`가 환승 도보 350m와 하버사인 공식을 한 번 더
  적는다. 갈리면 「번들이 350m라 부른 것」과 「카드가 재는 도보권」이 다른 자가 된다. 지금은 검사 둘이 막는다 —
  `test_빌드_상수가_worker_rules와_같다`(값)와 `번들의 환승 거리를 Worker가 다시 재도 같은 값이 나온다`(공식).
  없애려면 값을 번들에 실어 Worker가 읽게 하거나 빌드를 JS로 옮겨야 하는데, 둘 다 이 티켓보다 크다
- **route_links 「쌍당 최단 1개」가 막는 경로.** 노선 쌍에 환승 지점이 하나뿐이라, 그 한 자리가 승차 지점보다
  앞 순번이면 그 쌍으로는 경로가 안 나온다. 값이 노선망마다 다르다(§6-3) — 3km 넘게 떨어진 쌍 400개에서
  개편 전은 「경로 없음」이 **0**인데 개편 후는 **18(4.5%)**이다. 개편 후 노선망에서 이 결정이 실제로
  답을 지우고 있으므로, 쌍당 둘까지 두는 것을 티켓 5·6 어름에서 다시 본다(ADR-0008 결정 1).
  4.5% 중 얼마가 「원래 3회 이상 걸리는 쌍」이고 얼마가 「1개 제한 탓」인지는 아직 안 갈랐다
- **경로 키에 두 지점을 더했다(2026-09-04).** 스펙 Q12가 적은 칸은 노선망·정류장·노선뿐인데, 그것만으로는
  「출발 지점에서 몇 m 걷기」와 지표의 예상 시간·도보 합계를 되살릴 수 없다 — 도보권 후보의 거리는 시민이 고른
  두 지점에서 재는 값이라 번들에 없다. 빼면 다른 경로 카드의 예상 시간이 기본 카드와 **다른 자로 잰 값**이 되어
  견줄 수가 없다. 요청 매개변수로 붙이는 길도 있지만 그러면 「키 하나로 열린다」(User Story 34)가 깨진다.
  치르는 값은 둘이다 — 키 길이 약 60자, 그리고 **경로 키를 남에게 보내면 출발·도착 좌표가 함께 간다**.
  뒤엣것은 링크를 공유해도 열리게 하는 이상 어느 방법으로도 피할 수 없다(지점이 어딘가에는 있어야 한다)
- **서방사거리육교의 어긋남.** 통폐합 CSV는 계림사거리에 흡수·폐지됐다고 적었는데 개편 후 노선안(간선19 · 간선39 · 419)에는
  그대로 있다. 노선안을 고쳐 읽지 않고 비고만 붙인다(§7-3 Q3). 시가 자료를 고치면 다시 본다
